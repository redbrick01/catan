# 기본 플레이어봇 설계 고려사항

작성일: 2026-05-26

## 목적

이 문서는 기본 플레이어봇 구현 전에 합의해야 할 설계 기준과 주의사항을 정리한다.

세부 단계별 구현 계획서는 별도 문서로 나중에 작성한다. 이 문서는 구현 순서를 세밀하게 고정하기보다, 봇 기능 전체가 따라야 할 방향을 정한다.

## 최종 방향

```text
온라인 모드 기준 봇은 서버 컴퓨터에서 실행한다.
봇은 일반 플레이어 좌석을 차지한다.
봇 행동은 서버 권위 규칙을 통과한다.
봇은 게임 진행을 멈추지 않는 것을 최우선으로 한다.
첫 버전은 basic 난이도만 지원한다.
```

## 서버 봇을 기준으로 삼는 이유

온라인 게임에서는 서버가 이미 방 상태와 게임 상태의 권위자다.

따라서 봇이 클라이언트 브라우저에서 돌면 다음 문제가 생긴다.

```text
어느 브라우저가 봇을 대신 조작하는지 애매해진다.
방장이 새로고침하면 봇 행동이 끊길 수 있다.
클라이언트마다 봇 판단이 다르게 실행될 수 있다.
비공개 정보 접근 범위가 불명확해진다.
```

서버 봇은 이 문제를 줄인다.

```text
봇 행동 실행 위치가 하나다.
모든 클라이언트는 서버 state만 받는다.
봇은 WebSocket 연결 없이도 방에 남아 있을 수 있다.
서버가 기존 command 검증을 재사용할 수 있다.
```

## 오프라인 모드와의 관계

오프라인 모드까지 봇을 바로 지원할지는 구현 단계에서 결정한다.

권장 방향:

```text
1차 구현은 온라인 서버 봇을 우선한다.
봇 판단 함수는 가능하면 순수 함수에 가깝게 작성한다.
나중에 오프라인 script.js에서도 같은 평가 함수를 옮기거나 공유할 수 있게 한다.
```

오프라인을 즉시 포함하면 UI와 상태 흐름을 동시에 건드려야 하므로 범위가 커질 수 있다.

## 봇 상태 모델

봇은 room player와 game player 양쪽에 표시되어야 한다.

room player 예시:

```js
{
  id: "bot_abc123",
  seatIndex: 2,
  name: "봇 1",
  color: "#70c1b3",
  connected: true,
  left: false,
  isBot: true,
  botDifficulty: "basic"
}
```

game player 예시:

```js
{
  id: 2,
  onlinePlayerId: "bot_abc123",
  name: "봇 1",
  isBot: true,
  botDifficulty: "basic",
  resources: {},
  dev: []
}
```

주의:

```text
봇은 실제 socket이 없다.
봇은 reconnect 대상이 아니다.
봇은 connected 검사에서 항상 준비된 플레이어로 취급한다.
봇의 token은 외부 클라이언트 인증에 쓰지 않는다.
```

게임 시작 조건은 다음처럼 분리한다.

```text
최소 사람 수: 1명
총 플레이어 수: 3~4명
봇 최대 수: 총 플레이어 수가 4명을 넘지 않는 범위
시작 가능 조건: 실제 사람은 모두 connected, 봇은 ready로 간주
```

이 조건을 분리해야 "사람 1명 + 봇 2명"은 허용하면서도 "봇만 있는 자동 게임"은 막을 수 있다.

## 봇 command 실행 경로

봇은 socket이 없으므로 사람 클라이언트와 같은 인증 경로를 그대로 탈 수 없다.

권장 구조:

```text
handleClientCommand(socket, message)
-> 인증/room/player 확인
-> applyGameCommand(context, payload)
-> broadcast

runBotCommand(room, botPlayer, payload)
-> botPlayer가 room에 있고 isBot인지 확인
-> applyGameCommand(context, payload)
-> broadcast
```

핵심은 `applyGameCommand` 또는 그에 준하는 규칙 검증/상태 변경 경로를 공유하는 것이다.

```text
봇은 WebSocket 인증을 우회할 수 있다.
봇은 턴/자원/위치/카드/phase 검증을 우회하면 안 된다.
```

## 봇 실행 트리거

봇은 다음 시점에 실행될 수 있다.

```text
게임 시작 직후 setup actor가 봇일 때
사람 행동 후 다음 actor가 봇이 되었을 때
주사위 7로 discard pending 대상에 봇이 포함될 때
강도 이동 actor가 봇일 때
피해자 선택 actor가 봇일 때
개발 카드 pending actor가 봇일 때
플레이어 거래 응답 대상에 봇이 포함될 때
턴 종료 후 다음 active player가 봇일 때
```

봇 실행기는 한 방에서 하나만 돌아야 한다.

예약된 봇 행동은 실행 직전에 여전히 유효한지 확인한다.

확인 대상:

```text
room.status
room.revision
game.phase
active seat 또는 setupIndex
pending action 종류
pending actor
bot player가 아직 room에 있는지
```

취소 대상:

```text
방 종료
새 게임 시작
사람이 나가면서 방 상태 변경
revision 변경으로 이미 다른 행동이 처리됨
pending action 종류 변경
봇이 더 이상 현재 actor가 아님
```

## 봇 행동 지연

봇이 너무 즉시 행동하면 사람 입장에서 무슨 일이 일어났는지 따라가기 어렵다.

권장:

```text
행동 사이 300~800ms 지연
테스트 환경에서는 지연을 줄이거나 끌 수 있는 옵션
방 종료/게임 종료 시 예약된 봇 행동 취소
```

## 봇 평가 함수 기본 방향

첫 버전은 단순 점수 기반으로 충분하다.

### 정착지 평가

```text
생산 확률
자원 다양성
초반 건설 자원
밀/광석 장기 가치
항구 가치
기존 내 정착지와의 자원 보완
확장 가능성
```

### 도시 평가

```text
생산 기대값이 높은 정착지
6/8이 붙은 정착지
희소 자원을 생산하는 정착지
이미 막힌 강도 타일만 붙은 정착지는 감점
```

### 도로 평가

```text
좋은 정착지 후보로 가까워지는 도로
막다른 길 감점
상대 건물에 막힐 가능성 감점
최장 교역로는 1차 기본 봇에서 낮은 가중치
```

### 개발 카드 평가

```text
도시/정착지/도로가 당장 불가능하면 구매 후보
기사 보너스 경쟁 가능성이 있으면 가산점
승점 카드 가능성은 공개하지 않고 내부 기대값으로만 취급
```

개발 카드 사용은 MVP 안에서도 범위를 나눠 처리한다.

```text
1차: 승점 보유, 기사 사용, 풍년 사용
2차: 독점 사용, 도로 건설 카드의 무료 도로 배치
```

도로 건설 카드는 pending action을 추가로 만들기 때문에 1차 안정화 뒤 붙이는 편이 안전하다.

### 교역 평가

```text
목표 건설에 필요한 부족 자원을 얻으면 가산점
희소 자원을 내주면 감점
상대가 1등이면 더 보수적으로 판단
```

## 기본 봇의 한계

첫 버전 봇은 다음을 잘하지 못해도 허용한다.

```text
장기 최장 교역로 계획
상대 손패 정확 추정
복잡한 다자간 견제
교역 심리전
포트 독점 전략
상대 개발 카드 추론
```

대신 다음은 반드시 해야 한다.

```text
합법 행동만 한다.
자기 차례를 끝낸다.
pending action을 처리한다.
비공개 정보를 노출하지 않는다.
서버를 죽이지 않는다.
```

공정성 원칙:

```text
기본 봇은 서버가 알고 있는 모든 비공개 정보를 전략에 사용하지 않는다.
상대의 정확한 개발 카드 종류는 판단에 사용하지 않는다.
상대 자원은 공개 정보 수준인 총량과 공개 행동 로그에서 추정 가능한 범위만 사용하는 것을 우선한다.
```

## UI 원칙

봇 UI는 새 게임 모드를 크게 만들기보다 기존 로비와 플레이어 카드에 자연스럽게 붙인다.

필수:

```text
로비에서 봇 추가/제거 버튼
봇 이름 표시
봇 배지 표시
봇 턴 중 조작 불가 표시
봇 행동 로그
```

보류:

```text
봇 성격 선택
봇 아바타
봇 난이도 상세 설정
봇 전략 프리셋
```

## 테스트 원칙

봇 테스트의 1차 목표는 실력이 아니라 안정성이다.

확인해야 할 것:

```text
봇이 포함된 게임이 시작되는가
초기 배치가 끝나는가
봇 턴이 끝나는가
7이 나와도 진행되는가
강도 흐름이 끝나는가
거래 pending이 남지 않는가
봇이 이겨도 게임이 종료되는가
사람 전용 게임이 회귀하지 않는가
```

자동 테스트는 WebSocket 수준에서 우선 작성한다.

봇 테스트는 재현 가능해야 한다.

권장 테스트 조건:

```text
NODE_ENV=test에서 봇 행동 지연 제거 또는 최소화
forced dice 사용
고정 보드 또는 고정 random seed 사용
고정 개발 카드 덱 사용
봇 행동 최대 횟수 제한
테스트 종료 시 예약된 bot timer 정리
```

브라우저 테스트는 다음을 확인한다.

```text
로비에서 봇이 보인다.
봇 추가/제거 버튼 상태가 맞다.
봇 행동이 로그로 보인다.
봇 턴 중 사람 버튼이 잘 비활성화된다.
상태가 여러 브라우저에 동기화된다.
```

## 다음 결정 사항

세부 계획서를 작성하기 전에 다음 결정을 내려야 한다.

```text
1차 범위에 오프라인 봇을 포함할지 여부
온라인 로비에서 허용할 최소 사람 수
봇 최대 수
봇 제거 허용 시점
봇 이름 자동 생성 규칙
봇 행동 지연 시간
테스트에서 봇 지연을 끄는 방법
```

권장 기본값:

```text
1차 범위: 온라인 서버 봇 우선
최소 사람 수: 1명
총 플레이어 수: 3~4명
봇 최대 수: 방 최대 인원 4명까지 빈자리만
봇 제거: lobby 상태에서만
봇 이름: 봇 1, 봇 2
행동 지연: 기본 500ms
테스트 지연: NODE_ENV=test에서 0ms 또는 매우 짧게
```
