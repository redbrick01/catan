# 기본 플레이어봇 전체 구현 로드맵

작성일: 2026-05-26

## 목적

이 문서는 Catan 프로젝트에 기본 플레이어봇을 추가하기 위한 전체 구현 흐름을 정의한다.

목표는 강한 AI를 만드는 것이 아니라, 사람 수가 부족할 때 봇이 빈 자리를 채워 3~4인 게임 흐름을 유지하게 만드는 것이다. 봇은 규칙을 위반하지 않고, 자기 턴을 멈춤 없이 처리하며, 최소한의 합리적인 선택을 하는 수준을 1차 목표로 한다.

## 핵심 목표

```text
사람 1~2명이 부족한 자리를 봇으로 채울 수 있다.
봇은 일반 플레이어와 같은 seatIndex를 가진다.
봇은 서버 컴퓨터에서 실행된다.
온라인 모드에서는 서버가 봇 행동을 자동으로 처리한다.
오프라인 모드는 가능하면 같은 봇 판단 로직을 재사용한다.
봇 때문에 게임이 pending 상태에서 멈추지 않는다.
봇 행동은 모든 클라이언트에 같은 상태로 동기화된다.
```

## 비목표

```text
강한 전략 AI
머신러닝 기반 AI
장기 수읽기
사람처럼 대화하는 봇
봇 간 협상 심리전
완벽한 최장 교역로 계획
공식 2인 변형 규칙 구현
```

이번 목표는 "잘하는 봇"이 아니라 "같이 플레이 가능한 기본 봇"이다.

## 기본 원칙

### 1. 봇은 일반 플레이어다

봇은 별도의 게임 객체가 아니라 기존 플레이어 모델에 속성을 더해 표현한다.

```js
{
  id: "bot_1",
  seatIndex: 2,
  name: "봇 1",
  color: "#70c1b3",
  isBot: true,
  botDifficulty: "basic"
}
```

게임 엔진 입장에서는 사람과 봇이 같은 자원, 건물, 개발 카드, 점수, 턴 순서를 가진다.

### 2. 봇 행동도 서버 검증을 통과해야 한다

온라인 모드에서 봇은 서버 내부에서 직접 상태를 조작하지 않는다. 가능하면 기존 command 처리 경로를 사용하거나, 같은 검증 함수를 호출해서 사람 플레이어와 동일한 규칙을 적용한다.

```text
사람: 브라우저 -> command -> 서버 검증 -> 상태 변경
봇: 서버 봇 실행기 -> command 또는 내부 액션 -> 서버 검증 -> 상태 변경
```

봇은 실제 WebSocket과 playerToken 인증 흐름을 거치지 않으므로, 구현 시에는 봇 전용 내부 실행 경로를 명확히 둔다.

```text
runBotCommand(room, botPlayer, payload)
-> 사람 command와 같은 검증/상태 변경 함수 호출
-> WebSocket 인증, requestId 응답, socket 전송만 생략
```

즉, 봇은 인증을 우회하되 규칙 검증을 우회하지 않는다.

### 3. 멈춤 방지가 최우선이다

봇 판단이 완벽하지 않아도 된다. 하지만 다음 상황에서 게임이 멈추면 안 된다.

```text
초기 배치
주사위 7
자원 버리기
강도 이동
강도 피해자 선택
개발 카드 추가 선택
도로 건설 카드의 무료 도로 배치
플레이어 거래 응답
턴 종료
```

모든 봇 행동에는 실패 fallback을 둔다.

### 4. 첫 버전은 기본 난이도 하나만 만든다

처음에는 `basic` 난이도만 구현한다.

```text
easy, normal, hard 난이도 분리는 이후 단계로 미룬다.
다만 평가 함수 구조는 나중에 난이도별 가중치를 넣을 수 있게 작성한다.
```

## 전체 구현 흐름

### Phase 0. 현재 구조 점검

목표:

```text
서버 권위 온라인 엔진에서 봇이 끼어들 지점을 확인한다.
오프라인 모드와 온라인 모드의 상태 차이를 확인한다.
기존 command, pending action, broadcast 흐름을 정리한다.
```

확인 대상:

```text
server.js의 room/player 모델
server.js의 matchState 모델
startGame, endTurn, rollDice 흐름
setup1/setup2 초기 배치 흐름
7/강도 pending action 흐름
player trade pending 흐름
script.js의 오프라인 게임 시작 흐름
```

완료 기준:

```text
봇 실행기를 어디에서 호출할지 정한다.
봇 플레이어가 상태 view에 어떻게 노출될지 정한다.
오프라인 봇 지원을 1차 범위에 넣을지 후속 범위로 둘지 정한다.
```

### Phase 1. 봇 플레이어 모델과 로비 제어

목표:

```text
방장이 온라인 로비에서 봇을 추가/제거할 수 있게 한다.
사람+봇 합산 인원으로 게임 시작 조건을 판단한다.
봇은 WebSocket 연결 없이 서버 소유 플레이어로 유지한다.
```

시작 조건은 사람 수와 총 좌석 수를 분리해서 판단한다.

```text
최소 사람 수: 1명
총 플레이어 수: 3~4명
봇 최대 수: 총 플레이어 수가 4명을 넘지 않는 범위
게임 시작 조건: 사람+봇 합산 3명 이상, 실제 사람은 모두 connected, 봇은 항상 ready
```

주요 변경:

```text
room.players에 isBot 필드 추가
봇 생성용 player id/token 정책 추가
addBot/removeBot command 추가
로비 참가자 목록에 봇 표시
게임 시작 조건에서 connected 검사 시 봇 예외 처리
```

주의:

```text
봇은 disconnected 상태가 아니다.
봇 제거는 lobby 상태에서만 허용한다.
게임 시작 후 봇 제거는 1차 범위에서 제외한다.
```

### Phase 2. 봇 턴 실행기

목표:

```text
현재 행동해야 하는 플레이어가 봇이면 서버가 자동으로 행동을 실행한다.
봇 행동 사이에는 짧은 지연을 둬서 클라이언트가 상태 변화를 따라갈 수 있게 한다.
```

기본 실행 흐름:

```text
state broadcast 후 현재 actor 확인
actor가 봇이면 bot runner 예약
pending action이 있으면 pending 종류별 봇 응답 실행
일반 턴이면 주사위/행동/턴 종료 실행
행동 후 상태 broadcast
다음 actor가 봇이면 다시 예약
```

완료 기준:

```text
봇이 아무 행동을 못 해도 턴을 종료한다.
봇 행동 중 오류가 나도 서버가 죽지 않는다.
동시에 여러 bot runner가 같은 방에서 중복 실행되지 않는다.
방 종료/새 게임/revision 변경/pending 종류 변경 시 오래된 봇 예약이 실행되지 않는다.
```

### Phase 3. 초기 배치 봇

목표:

```text
setup1/setup2에서 봇이 정착지와 도로를 자동 배치한다.
```

기본 평가 요소:

```text
숫자 토큰 생산 확률
자원 다양성
초반 자원 가치: 나무, 벽돌, 밀, 양
중후반 자원 가치: 밀, 광석
두 번째 정착지의 자원 보완
항구와 생산 자원 조합
주변 확장 가능성
```

도로 선택:

```text
방금 지은 정착지와 연결된 빈 도로 중 선택한다.
가능하면 다음 정착지 후보 방향을 선호한다.
판단 실패 시 합법 도로 중 하나를 선택한다.
```

완료 기준:

```text
봇 포함 게임이 setup1/setup2를 끝까지 통과한다.
봇의 초기 배치가 거리 규칙과 도로 연결 규칙을 위반하지 않는다.
```

### Phase 4. 일반 턴 기본 행동

목표:

```text
봇이 자기 턴에 주사위를 굴리고, 가능한 기본 행동을 수행한 뒤 턴을 종료한다.
```

우선순위:

```text
1. 즉시 승리 가능한 행동
2. 도시 건설
3. 정착지 건설
4. 정착지 후보로 향하는 도로 건설
5. 개발 카드 구매
6. 은행/항구 교역으로 위 행동 달성
7. 턴 종료
```

초기 제한:

```text
한 턴에 실행할 건설/구매 행동 수를 제한한다.
봇이 너무 긴 연쇄 행동을 하지 않게 한다.
교역은 은행/항구 교역만 능동적으로 사용한다.
권장 기본값은 한 턴 최대 2개 주요 행동과 목표 달성을 위한 은행/항구 교역 1회다.
```

완료 기준:

```text
봇이 play phase에서 주사위 굴림부터 턴 종료까지 자동 처리한다.
봇이 자원 부족, 합법 위치 없음, 카드 없음 상황에서도 멈추지 않는다.
```

### Phase 5. 7/강도/pending action 처리

목표:

```text
7이 나오거나 기사 카드로 강도 흐름이 시작되어도 봇이 자동 응답한다.
```

자원 버리기:

```text
버려야 할 수량을 정확히 맞춘다.
가장 많이 가진 자원부터 버린다.
현재 목표에 필요한 희소 자원은 가능하면 보존한다.
```

강도 이동:

```text
내 생산 타일은 피한다.
상대가 생산하는 좋은 숫자 타일을 선호한다.
승점이 높은 상대를 우선 견제한다.
피해자는 자원이 있고 점수가 높은 플레이어를 우선한다.
```

완료 기준:

```text
봇이 discardForSeven, moveRobber, chooseRobberVictim을 자동 처리한다.
pending action이 봇 차례에서 방치되지 않는다.
```

### Phase 6. 개발 카드 기본 처리

목표:

```text
봇이 개발 카드를 사기만 하고 방치하지 않게 한다.
```

개발 카드는 pending action과 추가 선택지가 많으므로 MVP 내부에서도 우선순위를 나눈다.

기본 정책:

```text
기사: 강도 이동 이득이 있거나 최대 기사 보너스 경쟁이 가능하면 사용
풍년: 다음 목표에 부족한 자원 2개 선택
독점: 상대가 많이 가지고 있을 가능성이 큰 자원 선택
도로 건설: 정착지 후보 쪽으로 합법 도로 배치
승점: 자동 보유
```

1차 권장 범위:

```text
승점: 보유만으로 처리
기사: 강도 흐름 자동 처리까지 포함
풍년: 부족 자원 2개 선택
```

2차 권장 범위:

```text
독점: 상대 보유 추정 기반 자원 선택
도로 건설: 무료 도로 pending 1~2회 자동 처리
```

완료 기준:

```text
봇의 개발 카드 사용이 구매 턴 제한, pending action, 승점 계산과 충돌하지 않는다.
```

### Phase 7. 거래 응답

목표:

```text
사람이 봇에게 플레이어 거래를 제안했을 때 봇이 자동 수락/거절한다.
```

1차 범위:

```text
봇은 먼저 사람에게 거래를 제안하지 않는다.
봇은 은행/항구 교역만 능동적으로 사용한다.
사람의 제안에는 목표 달성 여부를 기준으로 응답한다.
```

거절 기준:

```text
봇의 다음 목표에서 멀어진다.
상대가 즉시 승점 행동을 할 가능성이 크다.
1등 플레이어에게 과도하게 유리하다.
봇이 희소하게 필요한 자원을 내줘야 한다.
```

완료 기준:

```text
봇 대상 거래 제안이 pending 상태로 방치되지 않는다.
```

### Phase 8. UI와 로그

목표:

```text
사람 플레이어가 봇 행동을 이해할 수 있게 표시한다.
```

필수 표시:

```text
로비 참가자 목록의 봇 배지
게임 중 플레이어 카드의 봇 표시
봇 턴 중 조작 비활성화
봇 행동 로그
봇이 생각 중임을 과하지 않게 표시
```

로그 예시:

```text
봇 1: 주사위를 굴렸습니다.
봇 2: 마을을 건설했습니다.
봇 1: 은행과 교역했습니다.
봇 2: 강도를 이동했습니다.
```

주의:

```text
비공개 정보가 로그에 노출되면 안 된다.
봇이 훔친 자원 종류를 상대에게 공개하지 않는다.
봇의 개발 카드 종류를 불필요하게 공개하지 않는다.
```

### Phase 9. 안정화와 회귀

목표:

```text
봇 포함 게임이 실제 플레이 흐름에서 멈추지 않는지 검증한다.
```

중점 시나리오:

```text
사람 1 + 봇 2
사람 2 + 봇 1
사람 2 + 봇 2
온라인 방장 + 봇
초기 배치 전체 자동 진행
7 발생
강도 피해자가 봇인 경우
강도 actor가 봇인 경우
봇 대상 플레이어 거래
봇이 승리 조건에 도달하는 경우
사람이 나갔을 때 남은 봇 처리
```

완료 기준:

```text
봇 포함 온라인 게임을 여러 턴 진행할 수 있다.
서버 콘솔에 치명 오류가 없다.
브라우저 콘솔에 반복 오류가 없다.
오프라인 기존 3~4인 게임이 회귀하지 않는다.
```

## 주요 위험

### 위험 1. 봇 runner 중복 실행

같은 방에서 여러 타이머가 동시에 봇 행동을 실행하면 상태가 꼬일 수 있다.

대응:

```text
room 단위 botRunnerActive 플래그를 둔다.
revision 또는 action id를 확인한다.
상태 변경 후 다음 봇 실행은 새로 예약한다.
예약 시점의 room.status, game.phase, pending kind, active/setup actor를 함께 저장하고 실행 직전에 다시 확인한다.
```

### 위험 2. pending action 방치

봇이 discard, robber, trade response 같은 응답을 하지 않으면 게임이 멈춘다.

대응:

```text
pending action 종류별 봇 응답 함수를 먼저 만든다.
판단 실패 시 합법 fallback을 실행한다.
```

### 위험 3. 서버 내부 직접 조작으로 규칙 우회

봇이 상태를 직접 바꾸면 사람 플레이어와 다른 규칙이 적용될 수 있다.

대응:

```text
기존 command handler 또는 공통 검증 함수를 재사용한다.
봇 전용 예외는 최소화한다.
```

### 위험 4. 봇이 너무 약해서 게임성이 낮음

기본 봇은 강하지 않을 수 있다.

대응:

```text
초기 배치 평가를 우선 튜닝한다.
도시/정착지/도로 우선순위만 안정적으로 잡는다.
강한 봇은 후속 목표로 분리한다.
```

### 위험 5. 비공개 정보 노출

서버 봇은 전체 정보를 볼 수 있으므로 로그와 상태 view에서 정보가 새면 안 된다.

대응:

```text
봇 판단은 서버 내부에서만 사용한다.
클라이언트 view에는 기존 비공개 필터를 유지한다.
로그에는 공개 가능한 결과만 기록한다.
기본 봇은 상대의 정확한 개발 카드 종류처럼 사람도 알 수 없는 비공개 정보를 전략 판단에 사용하지 않는다.
```

## MVP 완료 기준

```text
온라인 로비에서 방장이 봇을 추가/제거할 수 있다.
사람+봇 합산 3~4명으로 게임을 시작할 수 있다.
봇이 초기 배치를 자동 완료한다.
봇이 일반 턴을 자동 완료한다.
봇이 7/강도/pending action을 자동 처리한다.
봇이 기본 건설, 개발 카드 구매, 은행/항구 교역을 수행한다.
봇 대상 플레이어 거래가 방치되지 않는다.
봇 행동이 모든 클라이언트에 동기화된다.
봇 포함 게임이 여러 턴 동안 멈추지 않는다.
기존 오프라인/온라인 사람 전용 게임이 회귀하지 않는다.
```

## 최종 판단 기준

이번 봇 작업의 성공 기준은 다음 문장으로 정리한다.

```text
봇은 영리하지 않아도 된다.
하지만 사람 1~2명이 부족해도 게임 한 판을 실제로 굴릴 수 있어야 한다.
```
