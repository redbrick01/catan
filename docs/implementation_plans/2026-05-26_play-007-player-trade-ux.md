# 수정 계획서: PLAY-007 플레이어 간 교환 UX 개선

작성일: 2026-05-26  
관련 문제 문서: `docs/known_issues/2026-05-26_playability-issues.md`  
대상 파일: `script.js`, `styles.css`

## 1. 목적

플레이어 간 교환 제안 작성과 수락 흐름을 더 자연스럽고 오류가 적게 만든다.

## 2. 현재 문제

현재 교환 모달은 상대 선택, 제공 자원, 요청 자원을 지정하고 상대가 수락 또는 거절할 수 있다.

남은 문제:

- 제안 작성 중 보유량보다 큰 수량을 올릴 수 있다.
- 보유량 부족은 제안 버튼을 누른 뒤에야 로그로 알려준다.
- 같은 화면에서 상대가 수락하는 방식이라 실제 원격 멀티플레이 수락처럼 느껴지지 않는다.
- 제안 내용을 수정하려면 모달을 다시 열어야 한다.

## 3. 수정 범위

첫 개선 범위:

- 제안 작성 중 보유량 초과 선택을 버튼 비활성화로 막는다.
- 제공 또는 요청이 0장인 상태에서는 제안 버튼을 비활성화한다.
- 제안 확인 화면에서 `수정` 버튼을 제공해 작성 화면으로 돌아갈 수 있게 한다.
- 수락 직전에 자원 보유량 재검증은 유지한다.

이번 범위에서 제외:

- 네트워크 기반 멀티플레이
- 비밀 수락 화면 또는 패스앤플레이 가림 화면
- 교환 제안 목록과 비동기 대기 상태

## 4. 구조 변경 여부

이 계획의 1차 수정은 전체 구조 변경 없이 진행한다.

1차 범위:

- 현재 모달 안에서 수량 선택 제한, 제안 버튼 활성화 조건, 수정 버튼을 추가한다.
- 제안과 수락은 기존처럼 같은 로컬 화면에서 처리한다.
- 자원 이동은 기존 클라이언트 상태에서 즉시 반영한다.

전체 구조 변경이 필요한 범위:

- 상대 플레이어가 자기 화면에서만 제안을 확인하고 수락한다.
- 교환 제안을 게임 상태에 저장하고 대기/취소/만료 상태를 둔다.
- 원격 멀티플레이에서 서버가 교환 유효성을 검증한다.
- 여러 제안을 동시에 관리한다.

따라서 이번 계획은 "현재 로컬 모달 UX 개선"이며, 멀티플레이 교환 시스템은 별도 대형 작업이다.

## 5. 구현 계획

1. `addResourceEditor()`에서 각 자원 row의 `plus` 버튼이 `values[type] >= owner.resources[type]`이면 비활성화되도록 한다.
2. `minus`, `plus`, 상대 변경 시 row 상태와 요약을 함께 갱신하는 렌더링 방식을 정리한다.
3. `offerTotal`과 `requestTotal`이 모두 1 이상일 때만 `제안` 버튼을 활성화한다.
4. 제안 확인 모달에 `수정` 버튼을 추가한다.
5. `수정`을 누르면 기존 선택값을 유지한 작성 화면으로 돌아가도록 상태 보존 방식을 결정한다.
6. 수락 직전 `hasResources()` 재검증은 그대로 유지한다.

## 6. 세부 구현 체크리스트

대상 함수:

- `showPlayerTradeModal()`
- 내부 함수 `resourceText(resources)`
- 내부 함수 `updateSummary()`
- 내부 함수 `addResourceEditor(title, owner, values)`
- 내부 함수 `renderRequestGroup()`
- `hasResources(player, cost)`
- `resourceCount(player)`

권장 리팩터링:

- 현재 `showPlayerTradeModal()` 내부에 상태와 렌더링이 모두 섞여 있다.
- 큰 구조 변경 없이 다음 지역 함수를 추가한다.
  - `renderEditor()`
  - `renderReview(partner)`
  - `updateProposeState()`
  - `syncEditorButtons(group)`

제안 작성 상태:

```js
const tradeDraft = {
  partnerId: Number(partnerSelect.value),
  offer,
  request
};
```

버튼 비활성화 규칙:

- `minus.disabled = values[type] <= 0`
- `plus.disabled = values[type] >= owner.resources[type]`
- `propose.disabled = offerTotal <= 0 || requestTotal <= 0`
- 상대 변경 시 `request`는 0으로 초기화한다.
- 현재 플레이어 제공 자원은 상대 변경 후에도 유지한다.

확인 화면 버튼:

- `거절`: 교환을 취소하고 모달을 닫는다.
- `수정`: 작성 화면으로 돌아가되 기존 `offer`, `request`, `partnerId`를 유지한다.
- `수락`: 수락 직전 양쪽 보유량을 재검증하고 자원을 이동한다.

수락 직전 재검증:

```js
if (!hasResources(player, offer)) ...
if (!hasResources(partner, request)) ...
```

이 검증은 버튼 제한과 별개로 반드시 유지한다.

로그 정책:

- 제안 시점에는 자원이 이동하지 않는다.
- 거절 시 거절 로그만 남긴다.
- 수락 시 제공/획득 요약 로그를 남긴다.
- 수정 버튼은 로그를 남기지 않는다.

수정하지 않을 것:

- 은행 재고
- 항구 교환 비율
- 교환 가능 타이밍 `canTakePostRollAction()`
- 플레이어 간 교환이 은행을 거치지 않는 구조

## 7. 테스트 시나리오

### TC-001: 보유량 초과 제공 차단

사전 조건:

- 현재 플레이어가 목재 1장 보유

절차:

1. 플레이어 교환 모달을 연다.
2. 목재 제공 `+` 버튼을 누른다.
3. 다시 `+` 버튼 상태를 확인한다.

기대 결과:

- 목재 제공 수량은 1에서 멈춘다.
- `+` 버튼은 비활성화된다.

### TC-002: 상대 보유량 초과 요청 차단

사전 조건:

- 선택한 상대가 벽돌 2장 보유

기대 결과:

- 벽돌 요청 수량은 2를 넘을 수 없다.

### TC-003: 빈 제안 버튼 비활성화

기대 결과:

- 제공 0장, 요청 0장일 때 제안 버튼은 비활성화된다.
- 제공만 있고 요청이 없을 때도 비활성화된다.
- 요청만 있고 제공이 없을 때도 비활성화된다.
- 양쪽 모두 1장 이상이면 활성화된다.

### TC-004: 확인 화면에서 수정 가능

절차:

1. 제공과 요청을 선택한다.
2. 제안 버튼을 누른다.
3. 확인 화면에서 수정 버튼을 누른다.

기대 결과:

- 작성 화면으로 돌아온다.
- 기존 선택값이 유지된다.
- 다시 제안할 수 있다.

### TC-005: 수락 직전 자원 부족 차단

사전 조건:

- 제안 확인 화면에 들어간 뒤, 테스트 헬퍼로 현재 플레이어 또는 상대의 자원을 줄인다.

기대 결과:

- 수락 버튼을 눌러도 자원 이동이 발생하지 않는다.
- 부족 로그가 남는다.

### TC-006: 정상 수락 자원 이동

사전 조건:

- 현재 플레이어가 목재 1장 제공
- 상대가 벽돌 1장 제공

기대 결과:

- 수락 후 현재 플레이어 목재 -1, 벽돌 +1
- 상대 플레이어 목재 +1, 벽돌 -1
- 은행 재고는 변하지 않는다.

## 8. 완료 기준

- 플레이어가 가진 수량보다 많이 제공하도록 선택할 수 없다.
- 선택한 상대가 가진 수량보다 많이 요청하도록 선택할 수 없다.
- 주고받을 자원이 각각 1장 이상일 때만 제안할 수 있다.
- 확인 화면에서 거절, 수정, 수락이 모두 가능하다.
- 수락 직전 자원이 변한 경우 교환이 차단된다.

## 9. 검증 방법

- `node --check script.js`
- 현재 플레이어와 상대에게 제한된 자원을 부여한다.
- 보유량 한도에서 `+` 버튼이 비활성화되는지 확인한다.
- 0:1 또는 1:0 교환 제안이 불가능한지 확인한다.
- 확인 화면에서 `수정` 후 기존 선택값이 유지되는지 확인한다.
- 수락 전 자원을 줄인 상태에서 교환이 차단되는지 확인한다.

## 10. UI 세부 기준

- 수량 조절 버튼은 항상 같은 크기를 유지한다.
- 비활성화된 `+` 버튼은 흐리게 보이되 레이아웃이 흔들리지 않는다.
- 확인 화면에는 제공/요청 내역을 한 줄씩 명확히 보여준다.
- `수정`, `거절`, `수락` 버튼 순서는 사용자가 실수로 수락하지 않도록 `수정`, `거절`, `수락` 순서를 권장한다.

## 11. 위험 요소

- 현재 `showPlayerTradeModal()` 내부 상태가 지역 변수라, 수정 화면 복귀 시 상태 보존 구조가 복잡해질 수 있다.
- DOM을 부분 갱신하다가 버튼 상태와 표시 수량이 어긋날 수 있다.
- 상대 변경 시 이전 요청값 초기화 정책을 명확히 유지해야 한다.

## 12. 롤백 방법

교환 모달의 버튼 비활성화와 수정 버튼 로직을 제거하고 기존 제안/수락 흐름으로 되돌린다.
