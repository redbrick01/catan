# 3단계 UX 개선 구체화 계획

작성일: 2026-05-27

## 목적

현재 Katan은 기본 동작과 주요 규칙 흐름이 구현된 상태다. 3단계 UX 개선의 목표는 기능을 추가로 늘리기보다, 플레이어가 현재 상태와 다음 행동을 즉시 이해하고 실수 없이 조작할 수 있게 만드는 것이다.

기준 문장:

```text
동작하는 게임에서 편하게 플레이할 수 있는 게임으로 올린다.
```

## 적용 범위

대상 파일:

```text
index.html
styles.css
script.js
docs/test_plans/
docs/final_reports/
```

주요 UI 영역:

- 플레이어 간 교환 모달
- 7/도둑/개발 카드 등 pending action 모달
- 가이드 패널과 턴 진행 안내
- 게임 로그
- 모바일 레이아웃
- 온라인 방 참가, 재접속, 연결 끊김 안내

## UX 원칙

1. 플레이어가 지금 해야 할 행동을 화면 한 곳에서 분명히 알 수 있어야 한다.
2. 선택 가능한 행동과 불가능한 행동의 이유가 함께 보여야 한다.
3. 모달은 단순 확인 창이 아니라 "선택 -> 검토 -> 실행" 흐름을 제공해야 한다.
4. 온라인 상태 오류는 사용자 잘못, 서버 문제, 네트워크 문제를 구분해 안내해야 한다.
5. 모바일에서는 핵심 행동 버튼, 현재 턴, 보드가 먼저 보여야 한다.
6. 로그는 모든 이벤트를 같은 무게로 나열하지 않고 중요한 사건을 빠르게 찾을 수 있어야 한다.

## 상태 용어 정의

턴과 pending action 안내를 구현할 때 아래 용어를 구분한다.

| 용어 | 의미 | 예 |
| --- | --- | --- |
| `activePlayer` | 현재 턴을 가진 플레이어 | 주사위를 굴린 사람, 건설/교환을 진행할 수 있는 사람 |
| `actingPlayer` | 지금 실제로 행동해야 하는 플레이어 | 도둑을 이동해야 하는 사람, 약탈 대상을 골라야 하는 사람 |
| `pendingActors` | 동시에 또는 순차적으로 강제 행동을 처리해야 하는 플레이어 목록 | 7이 나와 자원을 버려야 하는 여러 플레이어 |
| `viewerPlayer` | 현재 브라우저를 보고 있는 온라인 플레이어 | 온라인에서 "나"로 표시되는 좌석 |
| `currentFocusPlayer` | 화면에서 가장 먼저 강조해야 하는 플레이어 | pending 중이면 `actingPlayer` 또는 `pendingActors`, 평상시에는 `activePlayer` |

우선순위:

```text
연결 끊김/방 종료 같은 blocking 상태
> pendingActors 또는 actingPlayer
> activePlayer
> 일반 대기 상태
```

오프라인은 여러 사람이 한 화면을 공유하므로 `내 차례` 대신 `현재 플레이어 차례`를 기본 문구로 사용한다. 온라인에서는 `viewerPlayer`와 `currentFocusPlayer`가 같을 때 `내 차례입니다` 또는 `내가 행동할 차례입니다`를 사용한다.

## UX-001 교환 제안 작성 UX 개선

### 현재 문제

- 플레이어 간 교환은 가능하지만 제안 작성 중 보유량, 상대 선택, 응답 상태를 한눈에 이해하기 어렵다.
- 잘못된 제안은 늦게 오류로 드러날 수 있다.
- 온라인에서는 요청자, 응답자, 대기자 각각의 화면 역할이 더 명확해야 한다.

### 개선 방향

- 교환 모달을 `제안 작성`, `응답 대기`, `응답 선택`, `결과 확인` 흐름으로 분리한다.
- 자원 선택 UI에 보유량과 선택량을 함께 표시한다.
- 선택량이 보유량을 넘으면 즉시 버튼을 비활성화하고 이유를 표시한다.
- 상대별 응답 상태를 `대기`, `수락`, `거절`로 표시한다.
- 교환 성사 조건을 안내한다.
- 같은 자원을 주고받는 의미 없는 제안은 차단한다.
- 제안 전 요약 문장을 제공한다.
- 1차 범위는 "모든 상대에게 제안하고 상대별 응답 상태를 표시"하는 방식으로 고정한다.
- 특정 플레이어만 지정하는 교환 제안은 1차 UX 개선 범위 밖으로 두되, UI 문구가 나중에 확장 가능하게 작성한다.

예:

```text
내가 줌: 목재 2, 벽돌 1
내가 받음: 밀 1
대상: 모든 상대
상태: 2명 응답 대기
```

### 구현 후보

- `showPlayerTradeModal()`
- `showPendingPlayerTradeModal()`
- `makePendingPlayerTradeView()` 관련 렌더링
- `onlineErrorMessage()`
- 교환 관련 CSS class 추가

### 완료 기준

- 보유량 초과 제안이 버튼 클릭 전 차단된다.
- 제안 요약이 항상 표시된다.
- 응답자 화면에서는 "내가 주는 것/받는 것" 관점으로 문장이 바뀐다.
- 모든 상대의 응답 상태가 화면에 보인다.
- 교환 결과가 로그와 모달에 같은 의미로 표시된다.
- 모든 상대 대상 제안인지, 특정 상대 대상 제안인지 혼동되는 문구가 없다.

## UX-002 pending action 안내와 선택 흐름 개선

### 현재 문제

- 7이 나왔을 때 자원 버리기, 도둑 이동, 약탈 대상 선택이 각각 동작하지만 안내 문구가 최소 수준이다.
- 대기자 화면에서 "왜 기다리는지"와 "누가 행동 중인지"가 충분히 명확하지 않을 수 있다.
- 새로고침/재접속 후 pending action이 복구되었을 때 사용자가 이어서 무엇을 해야 하는지 즉시 알기 어렵다.

### 개선 방향

- pending action마다 공통 헤더를 둔다.

```text
상황
해야 할 일
선택 조건
완료 후 다음 단계
```

- 자원 버리기 모달은 현재 선택량과 필요한 선택량을 고정 표시한다.
- 도둑 이동은 보드에서 선택 가능한 타일을 시각적으로 강조한다.
- 약탈 대상 선택은 대상별 자원 카드 총량과 선택 가능 여부를 표시한다.
- 대기자 화면에는 행동 중인 플레이어와 남은 인원을 표시한다.
- pending action 복구 시 "이전 진행 상태를 복구했습니다" 안내를 짧게 표시한다.
- pending action 모달이 떠 있을 때는 모달이 1차 안내를 담당한다.
- 가이드 패널은 같은 상황을 짧게 요약하고, 모달과 상충되는 행동 안내를 표시하지 않는다.
- discard처럼 여러 명이 행동해야 하는 경우 `pendingActors` 기준으로 남은 행동자 수와 내 행동 필요 여부를 분리해 표시한다.

### 구현 후보

- `showOnlinePendingActionModal()`
- `showOnlineDiscardForSevenModal()`
- `showOnlineChooseRobberVictimModal()`
- 도둑 이동 가능 타일 렌더링
- `guideTitle`, `guideText`
- `modalContent`, `modalActions`

### 완료 기준

- 각 pending action에서 플레이어가 해야 할 행동이 한 문장으로 명확하다.
- 선택 수량/조건이 실시간으로 갱신된다.
- 대기자 화면에서 남은 행동자 수가 표시된다.
- 새로고침 후 같은 pending action으로 돌아와도 같은 안내가 표시된다.
- 모달 안내와 가이드 패널 안내가 서로 다른 행동을 지시하지 않는다.

## UX-003 게임 로그 필터와 중요 이벤트 강조

### 현재 문제

- 게임 로그는 이벤트를 쌓지만 모든 로그가 같은 중요도로 보인다.
- 봇 행동, 자원 생산, 교환, 도둑, 승점 변화 같은 핵심 사건을 빠르게 찾기 어렵다.

### 개선 방향

- 로그 이벤트에 타입을 부여한다.

```text
turn
roll
resource
build
trade
dev
robber
score
system
bot
```

- 로그 상단에 필터 버튼 또는 중요 이벤트 토글을 추가한다.
- 중요 이벤트는 시각적으로 강조한다.
- 최신 턴의 로그를 구분한다.
- 긴 로그는 일정 길이 이후 접거나 스크롤 영역을 안정화한다.
- 1차 범위에서는 중요 이벤트 강조와 타입 class 부여를 우선한다.
- 로그 필터 UI는 1차 구현 후 로그 타입 구조가 안정되면 후속 작업으로 분리할 수 있다.

### 구현 후보

- `addLog()` 시그니처 확장
- `logOnlineStateDelta()`
- 로그 DOM 구조 변경
- `styles.css` 로그 타입 스타일

### 완료 기준

- 중요 이벤트만 보기 토글이 동작한다.
- 도둑, 교환 성사, 개발 카드, 승점 변화는 강조 표시된다.
- 봇 로그에는 비공개 정보가 노출되지 않는다.
- 로그가 길어져도 레이아웃이 밀리지 않는다.
- 필터 UI를 1차에서 제외한 경우에도 중요 이벤트 강조는 동작한다.

## UX-004 턴 진행 안내 강화

### 현재 문제

- 현재 플레이어와 가이드 문구는 있지만, 단계별로 가능한 행동과 다음 행동이 충분히 구조화되어 있지 않다.
- 온라인에서는 내 턴/상대 턴/봇 턴/pending action이 섞여 보일 수 있다.
- 누가 현재 진행 중인지 한눈에 들어오지 않을 수 있다.
- 자신의 차례가 왔을 때 화면 전체에서 직관적으로 확인하기 어렵다.

### 개선 방향

- 가이드 패널을 `현재 상황`, `가능한 행동`, `다음 추천 행동`으로 나눈다.
- 내 턴이면 주요 액션 버튼과 안내 문구를 같은 의미로 맞춘다.
- 상대 턴이면 기다리는 이유와 현재 플레이어를 강조한다.
- 봇 턴이면 자동 진행 중임을 표시한다.
- 행동 불가 버튼에는 비활성 이유를 tooltip 또는 짧은 보조 문구로 표시한다.
- 현재 진행 중인 플레이어 카드를 시각적으로 강조한다.
- 온라인에서 내 차례가 오면 별도의 `내 차례` 상태 배지와 가이드 강조 상태를 표시한다.
- 내 차례가 아닐 때는 `현재 진행: 플레이어명`, `대기 사유`, `예상 다음 행동`을 보여준다.
- pending action 중에는 일반 active player보다 실제 행동해야 하는 플레이어를 우선 강조한다.
- 봇이 진행 중이면 사람 플레이어와 다른 `봇 진행 중` 표시를 사용해 자동 처리 중임을 알린다.
- 모바일에서는 현재 진행 상태를 보드 위 또는 액션 버튼 근처에 고정해 스크롤 위치와 무관하게 볼 수 있게 한다.
- 화면의 상태 표시는 아래 세 위치를 기준으로 한다.
  - 상단 현재 플레이어 영역: `내 차례입니다`, `현재 진행: 플레이어명`, `봇 진행 중` 같은 짧은 상태 배지
  - 가이드 패널: 상황, 가능한 행동, 다음 추천 행동
  - 플레이어 카드: `진행 중`, `내 차례`, `대기`, `봇 진행 중`, `행동 필요` 상태 라벨
- 온라인과 오프라인의 문구를 분리한다.
  - 온라인 내 차례: `내 차례입니다`
  - 온라인 pending actor: `내가 행동할 차례입니다`
  - 온라인 상대 차례: `현재 진행: 플레이어명`
  - 오프라인: `플레이어명 차례입니다`

예:

```text
현재 상황: 내 턴, 주사위를 굴릴 차례입니다.
가능한 행동: 주사위 굴리기
다음 추천 행동: 굴림 후 자원을 확인하고 건설 또는 교환을 진행하세요.
```

추가 상태 예:

```text
내 차례입니다
현재 진행: 민수
민수가 도둑을 이동하는 중입니다
봇 Alpha가 턴을 진행 중입니다
지금은 대기 중입니다. 다음 차례까지 다른 플레이어의 행동을 기다리세요.
```

### 시각 강조 요구사항

- 현재 진행 플레이어 카드에는 active border, 배경 강조, 상태 라벨을 함께 적용한다.
- 내 차례일 때는 상단 현재 플레이어 영역, 가이드 패널, 주요 액션 영역 중 최소 두 곳에서 같은 상태가 보인다.
- 내 차례 강조는 색상만으로 의존하지 않고 텍스트 라벨을 함께 제공한다.
- 상대 차례일 때도 현재 진행 플레이어 이름이 화면 상단과 플레이어 카드에서 일치해야 한다.
- pending action 대상자는 일반 현재 턴 표시보다 우선순위가 높다.
- 연결 끊김이나 재접속 대기 중에는 내 차례 강조보다 연결 상태 경고가 우선한다.

### 완료 기준

- 내 턴/상대 턴/봇 턴/pending action이 가이드에서 구분된다.
- 활성 버튼과 안내 문구가 서로 모순되지 않는다.
- 행동 불가 상태의 이유가 최소 한 곳에 표시된다.
- 누가 현재 진행 중인지 화면을 처음 봐도 3초 안에 알 수 있다.
- 자신의 차례가 오면 `내 차례` 문구가 명확히 표시된다.
- 현재 진행 플레이어 카드가 시각적으로 강조된다.
- pending action 중에는 실제로 행동해야 하는 플레이어가 강조된다.
- 모바일 viewport에서도 현재 진행 상태가 스크롤 없이 확인된다.
- 오프라인에서는 `내 차례` 대신 `플레이어명 차례` 기준으로 표시된다.
- 상단 상태, 가이드 패널, 플레이어 카드의 진행 플레이어 이름이 일치한다.

## UX-005 모바일 레이아웃 재검토

### 현재 문제

- 모바일/좁은 viewport는 일부 보정이 있으나 실제 320px, 375px, 780px 시각 검증이 부족하다.
- 보드, 플레이어 카드, 액션 버튼, 로그, 모달이 서로 우선순위를 가져야 한다.

### 개선 방향

- 모바일 정보 우선순위를 정한다.

```text
1. 현재 턴/내가 해야 할 일
2. 보드
3. 주요 액션 버튼
4. 내 자원/개발 카드
5. 상대 요약
6. 로그
```

- 액션 버튼은 모바일에서 고정 하단 또는 보드 바로 아래에 배치하는 방안을 검토한다.
- 로그는 모바일에서 접힘 상태를 기본값으로 검토한다.
- 모달은 화면 높이에 맞춰 내부 스크롤을 사용한다.
- 긴 닉네임, 봇 배지, 자원 텍스트가 줄바꿈되어도 버튼과 겹치지 않게 한다.
- 1차 구현에서는 액션 버튼을 보드 바로 아래 또는 현재 정보 블록 아래의 일반 흐름에 둔다.
- 고정 하단 sticky 액션 바는 모달, 모바일 키보드, 작은 화면 겹침 문제가 없다는 검증 후 후속으로 검토한다.

### 검증 viewport

```text
320x568
375x667
390x844
414x896
768x1024
1280x720
1440x900
```

### 완료 기준

- 지정 viewport에서 가로 overflow가 없다.
- 모달 버튼이 화면 밖으로 밀리지 않는다.
- 주요 액션 버튼의 텍스트가 잘리지 않는다.
- 보드와 플레이어 카드가 서로 겹치지 않는다.

## UX-006 방 참가/재접속/연결 끊김 안내 개선

### 현재 문제

- 방 참가 실패, 서버 연결 실패, 연결 끊김, 재접속 대기 메시지가 존재하지만 회복 방법까지 충분히 안내하지 않는다.
- 사용자는 방 코드 오류, 서버 미실행, 네트워크 차단, 방 종료를 구분하기 어렵다.

### 개선 방향

- 오류를 원인별로 분류한다.

```text
방 코드 문제
닉네임 문제
방 정원 초과
이미 시작한 방
서버 연결 실패
서버 응답 시간 초과
연결 끊김
방 종료
재접속 대기
```

실제 오류 코드 매핑 초안:

| 코드/상황 | 사용자 메시지 방향 | 다음 행동 |
| --- | --- | --- |
| `ROOM_NOT_FOUND` | 방을 찾을 수 없음 | 방 코드 확인, 방장에게 새 링크 요청 |
| `ROOM_FULL` | 방 정원 초과 | 방장에게 빈 자리 확인 요청 |
| `GAME_ALREADY_STARTED` | 이미 시작한 방 | 새 방 생성 요청 |
| `INVALID_NAME` | 닉네임 문제 | 닉네임 다시 입력 |
| `REQUEST_TIMEOUT` | 서버 응답 지연 | 잠시 후 재시도, 방장 서버 상태 확인 |
| socket close/error | 서버 연결 실패 또는 끊김 | 같은 네트워크 확인, 방장 PC 서버 실행 여부 확인 |
| room ended | 방 종료 | 로비로 나가 새 방 생성 또는 참가 |

- 각 오류에는 사용자 행동 안내를 붙인다.

예:

```text
방을 찾을 수 없습니다. 방 코드가 맞는지 확인하거나, 방장에게 새 공유 링크를 요청하세요.
서버에 연결할 수 없습니다. 방장 PC에서 서버가 켜져 있는지 확인하세요.
연결이 끊겼습니다. 자동 재접속을 시도합니다. 같은 와이파이에 연결되어 있는지 확인하세요.
```

- 로비와 게임 화면 모두에 연결 상태 배지를 일관되게 표시한다.
- 자동 재접속 중에는 명령 버튼을 잠시 비활성화하고 이유를 표시한다.

### 구현 후보

- `onlineErrorMessage()`
- `connectOnlineSocket()`
- `handleOnlineMessage()`
- `setOnlineStatus()`
- `lobbyConnectionBadge`
- 게임 화면 연결 상태 배지 추가 검토

### 완료 기준

- 대표 오류 상황별 안내 문구가 다르다.
- 사용자가 다음 행동을 알 수 있다.
- 연결 끊김 중 명령 실패가 조용히 무시되지 않는다.
- 재접속 성공/실패가 로그와 상태 UI에 표시된다.

## 구현 순서

1. UX-004 턴 진행 안내 강화
2. UX-002 pending action 안내 개선
3. UX-001 교환 제안 작성 UX 개선
4. UX-006 연결/참가/재접속 안내 개선
5. UX-005 모바일 레이아웃 재검토
6. UX-003 게임 로그 필터와 중요 이벤트 강조

이 순서를 권장하는 이유는 플레이 중 가장 자주 확인하는 정보가 현재 진행자와 내 행동 여부이기 때문이다. 턴 안내를 먼저 고정한 뒤 pending action, 교환, 연결 오류, 모바일 배치를 맞추고, 로그 필터는 마지막에 구조를 안정화한다.
