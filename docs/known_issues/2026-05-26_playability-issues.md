# 플레이상 현재 카탄 문제점

작성일: 2026-05-26  
대상 파일: `script.js`, `index.html`, `styles.css`

## 1. 목적

현재 구현된 카탄을 실제 플레이 관점에서 검토해, 규칙 정확도와 플레이 경험을 떨어뜨리는 문제를 수정 가능한 작업 단위로 문서화한다.

이 문서는 문제 목록과 우선순위를 관리하고, 각 문제의 상세 수정 계획은 `docs/implementation_plans` 아래 개별 계획서에서 다룬다.

## 3. 상세 문제

### PLAY-001: 마을 건설 승리 체크 누락

현재 `buildSettlement()`는 마을을 건설한 뒤 점수가 변하지만 `checkWin()`을 호출하지 않는다.

영향:

- 일반 플레이 중 마지막 마을로 10점에 도달해도 즉시 승리하지 않을 수 있다.
- 다음 행동이나 턴 진행 전까지 승리 상태가 확정되지 않아 게임 종료 타이밍이 어긋난다.

관련 계획서:

- `docs/implementation_plans/2026-05-26_play-001-settlement-win-check.md`

### PLAY-002: 최대 기사력 승리 체크 누락

현재 `playKnight()`는 기사 카드 사용 후 `updateLargestArmy()`를 호출하지만, 최대 기사력 2점 획득 뒤 `checkWin()`을 호출하지 않는다.

영향:

- 3번째 기사 카드 사용으로 10점에 도달해도 즉시 승리하지 않을 수 있다.
- 보너스 점수로 승리하는 중요한 흐름이 불안정하다.

관련 계획서:

- `docs/implementation_plans/2026-05-26_play-002-largest-army-win-check.md`

### PLAY-003: 승점 카드 비공개 처리 미흡

현재 `visiblePoints()`는 승점 개발 카드를 모든 점수 표시 계산에 즉시 포함한다. 좌석과 플레이어 목록 UI도 이 점수를 그대로 표시한다.

영향:

- 승점 카드를 산 플레이어의 숨은 점수가 공개된다.
- 실제 카탄의 추리와 긴장감이 약해진다.
- 다른 플레이어가 승리 임박 여부를 과도하게 정확히 알 수 있다.

관련 계획서:

- `docs/implementation_plans/2026-05-26_play-003-private-victory-points.md`

### PLAY-004: 상대 자원 구성 공개

현재 좌석 UI는 모든 플레이어의 자원 종류별 수량을 표시한다.

영향:

- 도둑 대상 선택, 독점 카드 선택, 플레이어 교환 협상이 지나치게 계산적으로 변한다.
- 실제 카탄에서 공개되는 정보인 총 카드 수와 비공개 정보인 자원 종류가 구분되지 않는다.

관련 계획서:

- `docs/implementation_plans/2026-05-26_play-004-private-opponent-resources.md`

### PLAY-005: 항구 위치 모델 단순화

현재 항구는 해안 교차점 하나에만 붙는다. 실제 카탄 항구는 해안 모서리 주변의 두 교차점 중 하나에 정착지나 도시가 있으면 사용할 수 있다.

영향:

- 실제로는 항구를 사용할 수 있어야 하는 위치가 누락될 수 있다.
- 항구 표시와 사용 가능 판정이 직관적이지 않을 수 있다.

관련 계획서:

- `docs/implementation_plans/2026-05-26_play-005-harbor-edge-model.md`

### PLAY-006: 보드 랜덤 배치 밸런스 제약 부족

현재 보드 생성은 지형과 숫자 토큰을 섞지만, 높은 생산 숫자 6과 8의 인접 방지 같은 밸런스 제약이 없다.

영향:

- 특정 지역에 6/8이 몰려 초반 유불리가 커질 수 있다.
- 반복 플레이에서 보드 품질 편차가 커진다.

관련 계획서:

- `docs/implementation_plans/2026-05-26_play-006-board-randomizer-balance.md`

### PLAY-007: 플레이어 간 교환 UX 개선 필요

현재 플레이어 간 교환은 제안과 상대 수락 흐름은 있지만, 같은 화면에서 수동으로 수락하는 로컬 확인 방식에 가깝다. 또한 제안 작성 중 보유량 초과 선택을 즉시 막지 않는다.

영향:

- 핫시트 플레이 외 환경에서는 상대 수락의 의미가 약하다.
- 제안 중 뒤늦게 오류가 나와 흐름이 끊긴다.
- 교환 제안 작성이 실제 플레이보다 번거롭다.

관련 계획서:

- `docs/implementation_plans/2026-05-26_play-007-player-trade-ux.md`

## 7. 권장 묶음

작업은 다음 묶음으로 진행하는 것이 좋다.

### 묶음 A: 승리 조건 안정화

- PLAY-001
- PLAY-002

이 묶음은 규칙 정확도에 직접 연결되고 수정 범위가 작다. 먼저 처리하면 이후 비공개 점수 작업의 승리 체크 기준도 명확해진다.

### 묶음 B: 비공개 정보 정리

- PLAY-003
- PLAY-004

이 묶음은 표시 정책이 서로 연결된다. 승점 카드와 자원 구성 공개 범위를 같은 UI 원칙으로 맞춰야 한다.

### 묶음 C: 보드와 항구 규칙 개선

- PLAY-005
- PLAY-006

이 묶음은 게임 시작 시 만들어지는 보드 데이터에 영향을 준다. 항구 구조 변경 후 보드 생성 테스트를 함께 확장하는 것이 좋다.

### 묶음 D: 교환 사용성 개선

- PLAY-007

플레이어 간 교환은 모달 UX와 상태 관리가 중심이므로 단독으로 처리하는 편이 안전하다.

## 8. 전체 구조 변경 필요 여부

현재 7개 계획 중, 이 계획서에 적힌 1차 수정 범위만 구현한다면 프로젝트를 전체적으로 갈아엎어야 하는 항목은 없다.

다만 일부 문제는 "보드게임 보조 UI" 수준으로 고치면 국소 수정으로 충분하지만, "진짜 비밀 정보가 보장되는 멀티플레이 앱" 수준까지 목표를 올리면 구조 변경이 필요하다.

| ID | 1차 수정 범위 | 전체 구조 변경 필요 여부 | 구조 변경이 필요한 경우 |
| --- | --- | --- | --- |
| PLAY-001 | `buildSettlement()` 승리 체크 추가 | 필요 없음 | 해당 없음 |
| PLAY-002 | `playKnight()` 승리 체크와 승리 시 상태 정리 | 필요 없음 | 해당 없음 |
| PLAY-003 | 공개 점수와 실제 점수 계산 분리, 현재 플레이어 기준 표시 | 1차 수정은 필요 없음 | 플레이어별 비밀 손패를 실제로 보호하려면 사용자별 세션/뷰 분리 필요 |
| PLAY-004 | 상대 자원 종류별 수량을 좌석/목록에서 숨김 | 1차 수정은 필요 없음 | 완전한 핫시트 비공개를 원하면 턴 전환 가림 화면 또는 플레이어별 화면 필요 |
| PLAY-005 | 항구 데이터를 `vertexIds` 기반으로 변경 | 전체 갈아엎기는 아님, 보드 데이터 일부 마이그레이션 필요 | 보드 생성/렌더링을 공식 좌표 모델로 전면 교체할 경우 |
| PLAY-006 | 숫자 토큰 배치 재시도 알고리즘 추가 | 필요 없음 | 공식 프리셋, 시드 기반 저장/재현, 보드 편집기를 넣는 경우 |
| PLAY-007 | 교환 모달의 상태와 버튼 UX 개선 | 1차 수정은 필요 없음 | 원격 멀티플레이, 비동기 제안, 상대별 수락 권한을 구현하는 경우 |

### 구조 변경 후보

다음은 이번 1차 계획에서 바로 하지 않는 것이 좋다. 별도 대형 작업으로 분리해야 한다.

- 플레이어별 로그인, 세션, 권한이 있는 진짜 멀티플레이 구조
- 각 플레이어에게 자기 손패만 보여주는 별도 클라이언트 뷰
- 서버 권위형 게임 상태 관리
- 교환 제안을 서버에 저장하고 상대가 자기 화면에서 수락/거절하는 비동기 교환 시스템
- 보드 좌표, 항구, 타일, edge를 공식 맵 모델로 전면 재설계하는 작업
- 게임 저장/불러오기와 랜덤 시드 재현 시스템

### 현재 계획에서 유지할 경계

- 이 프로젝트는 현재 단일 HTML/CSS/JavaScript 기반 로컬 플레이 앱으로 유지한다.
- 정보 비공개는 "현재 화면 표시 정책" 수준에서 개선한다.
- 보안적 의미의 비밀 정보 보호는 이번 범위에 포함하지 않는다.
- 항구와 보드 밸런스는 기존 데이터 구조를 최대한 유지하며 필요한 부분만 확장한다.

## 9. 공통 검증 원칙

- `node --check script.js`로 문법 오류를 확인한다.
- 가능한 경우 `installTestHelpers()`를 활용해 특정 점수, 자원, 카드, 보드 상태를 빠르게 구성한다.
- 승리 조건 관련 수정은 9점 상태에서 해당 행동 하나로 10점이 되는 시나리오를 반드시 확인한다.
- 비공개 정보 관련 수정은 현재 플레이어 화면과 상대 플레이어 표시가 다르게 렌더링되는지 확인한다.
- UI 수정은 데스크톱과 모바일에서 텍스트 겹침과 가로 overflow를 확인한다.
